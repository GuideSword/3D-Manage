版本：0.2｜更新日期：2026-09-27｜状态：P0 已实现并通过自动化验收；P1–P6 为规划草案。

本文用于后续需求讨论、模块设计和开发验收。除 P0 库存一致性已交付外，标为“目标”的规则仍为建议基线，不代表已有能力。P0 字段、API、测试与限制见 [交付记录](P0_INVENTORY.md)，后续阶段开始前仍须核对代码变化。

配套执行入口：[分阶段改造路线图](superpowers/plans/2026-09-27-vertical-erp-roadmap.md)。原始 [MVP 需求](../需求文档.md) 保留为历史范围，本文描述后续演进。

## 1. 产品定位与范围

目标定位：面向小型 3D 打印工作室的轻量级垂直 ERP，统一管理销售订单、模型资料、生产任务、设备排程、耗材库存、采购及经营核算。

目标用户包括工作室负责人、接单人员、打印操作人员和仓库人员。首版采用一个部署对应一个组织，默认人民币、一个仓库、人工排程、联网操作；仓库数据模型保留扩展空间。

| 路径 | 收益 | 代价 | 结论 |
| --- | --- | --- | --- |
| 维持订单与库存工具 | 改动少、使用简单 | 难以追踪生产与利润 | 适合只需要记录业务的场景 |
| 演进为 3D 打印垂直 ERP | 复用现有基础，支持完整经营流程 | 需要数据迁移、生产规则和一致性保障 | 本文采用 |
| 建设通用 ERP | 行业覆盖面广 | 财务、行业配置和实施成本高 | 超出本文范围 |

阶段性完成标准：一笔订单可以追踪到生产任务、实际耗材消耗、打印结果、交付、收款和可解释的成本；一笔采购可以追踪到到货、批次和付款。

首轮不包含总账会计、税务申报、电子发票平台、多法人合并、多币种汇兑、全自动排产、复杂多层 MRP、设备远程控制、离线冲突同步。经营核算用于管理分析，专业会计可通过导出或外部系统集成实现。

### 2.1 必须理解的存储边界

`backend/utils/store.js` 当前维护 `users`、`orders`、`models`、`materials`、`stockLots`、`inventoryTxns`、`auditLogs`、`objectUploads` 集合。

- 文件模式将整体业务数据写入 `store.json`，使用进程内写队列。
- PostgreSQL 模式默认使用 `app_store` 表，将整体业务数据存为单行 JSONB；写入使用事务和 `SELECT ... FOR UPDATE`。
- 已有写队列和锁提供一定一致性保障，但这不等于独立业务表、外键约束或按批次锁定。
- `backend/db/schema.sql` 与 `backend/db/migrations.js` 属于 AI SQLite 数据域。新增 ERP 关系表必须使用独立业务迁移目录。
- P0 后 `backend/config/runtime.js` 中业务 schema 版本为 3，API 版本为 1；新增 commandReceipts，system/info 声明 inventoryRulesVersion=1。这不是关系表迁移，AI SQLite 版本不受影响。

### 2.2 与 ERP 规则的具体差距

1. 客户信息内嵌在订单中，还没有统一客户档案和去重流程。
2. 订单行有模型和材料描述，但没有稳定的生产规格版本、生产任务和实际耗用链路。
3. P0 已修复批次余额编辑绕过、创建缺期初流水和历史物理删除的问题；HTTP/CSV 共用库存服务，AI 共用摘要。删除耗材不再级联删除批次，订单有库存流水时禁止删除。关系约束与生产预留仍待后续阶段。
4. 盘点调整的 `qty` 保留“调整后绝对数量”兼容语义；P0 新流水另外记录 beforeQtyMg、afterQtyMg、deltaQtyMg。旧流水不补差额，历史批次保存切换余额并标记待核对；迁移不可直接把旧 qty 累加。
5. P0 保留旧订单状态转换，已禁止删除有关联库存流水的订单；完整生产、交付和收付款约束仍须分阶段实施。
6. 订单金额使用 JavaScript 浮点数和宽松字段归一化。财务和成本计算需要严格输入校验及精确金额表示。
7. P0 已统一 HTTP/CSV 库存写入及 HTTP/CSV/AI 确认订单创建；AI 库存工具仍为只读，不新增 AI 过账。后续模块同样必须调用公共业务服务。

## 3. 目标业务流程

### 3.1 销售到交付

客户档案 → 报价草稿 → 确认报价 → 销售订单 → 确认订单 → 生产任务 → 人工排程 → 耗材领用 → 打印报工 → 质检 → 发货 → 收款 → 经营分析。

报价模块上线前可手工录入订单金额。报价转订单必须保存价格、客户、规格快照，后续报价修改不影响已确认订单。

一条订单行允许分成多个生产任务，一个生产任务可包含多次打印尝试。每次失败打印仍记录设备时间和耗材，合格数量由质检结果决定，不能通过修改订单状态抹去损耗。

允许分批生产、分批交付和分次收款。交付数量不得超过可交付合格数量；按单生产的首版不自动形成成品库存，合格品可交付余额由报工、质检和交付记录计算。成品入库另行扩展。

### 3.2 采购到库存

供应商档案 → 采购草稿 → 确认采购 → 分批到货 → 到货验收 → 耗材批次入库 → 应付记录 → 付款登记。

首版到货时记录验收合格数量，只将合格数量入库。采购未到货数量可以取消，已入库数量只能通过退货/冲销处理。采购退货不得超过原入库未退数量及对应批次可用库存。

### 3.3 库存与生产

确认生产任务不立即扣库存。人员选择材料批次后可以预留，实际领用才扣现存数量；退料回到原批次，报废单独记录原因。

原料和打印后产品报废分开处理：已领耗材已计入任务成本，打印产品报废只影响产出，不能再次扣耗材。额外废弃的未领原料通过库存报废流水处理。

## 4. 领域术语与建议数据模型

模型是数字资产；生产规格是制造要求；耗材是库存物料；订单行是销售承诺；生产任务是执行计划；打印尝试是一次实际执行。禁止把上述对象混为一个可随时修改的订单对象。

下列名称为建议逻辑实体，不是现有表。实际字段定义、SQL 和 API 契约在对应阶段子设计中冻结。

| 实体 | 必要字段/关系 | 关键规则 |
| --- | --- | --- |
| Customer / Supplier | ID、名称、联系人、电话、地址、启用状态 | 停用保留历史引用；禁止仅按姓名自动合并 |
| Material | 编码、名称、材质、颜色、基本单位、启用状态 | 不改变已有流水的单位解释 |
| Warehouse / StockLot | 仓库、物料、批号、位置、数量、入库成本 | 首版创建默认仓库，保留原位置文本 |
| ModelAsset / ModelRevision | 模型 ID、版本、文件引用、校验值 | 已确认任务引用不可变版本，保留受保护访问 |
| ProductionSpec | 模型版本、打印参数、每件预估克重、时长、版本 | 首版单层耗材清单；确认时保存快照 |
| SalesOrder / SalesOrderLine | 客户引用及快照、稳定行 ID、数量、单价、币种、交期、版本 | 历史金额与地址不随档案更新而改变 |
| ProductionTask | 订单行、规格快照、计划数量、交期、状态、版本 | 订单行不能超量下达；补打关联原任务与原因 |
| PrintAttempt / QualityRecord | 任务、设备、起止时间、完成数量、合格/不合格数量、原因 | 实际产量和损耗可追溯；质检不能超报工量 |
| Equipment / ScheduleSlot | 名称、能力、状态；任务、设备、起止时间 | 维护/停用设备不可排程；同设备时段不能重叠 |
| StockReservation | 批次、任务、预留数量、已领/释放数量 | 预留不是库存扣减 |
| InventoryMovement | 批次、方向、变动量、来源单据/行、任务、操作者、时间、冲销引用 | 过账后不可改数量，不可物理删除 |
| PurchaseOrder / PurchaseLine | 供应商快照、物料、订购量、单位、单价、币种 | 分批收货并限制超量 |
| GoodsReceipt / PurchaseReturn | 采购行、验收量、入库批次、金额；退货引用 | 单据、流水及余额同事务更新 |
| Delivery / DeliveryLine | 订单行、发出数量、时间、物流信息 | 分批交付，退回须关联原交付 |
| Receivable / Payable | 来源单据、金额、到期日、冲减金额 | 首版订单确认建应收，验收入库建应付 |
| Payment / PaymentAllocation | 收/付款方向、金额、时间、渠道；应收/应付分配 | 未分配金额视为预收/预付；不能超额分配 |
| CostEntry | 任务/尝试、费用类型、数量、费率快照、金额、来源 | 来源唯一，禁止重复计费 |
| AuditEvent / CommandReceipt | 事件前后值、原因、操作者；幂等键与请求摘要 | 与业务写入原子提交 |

所有业务对象至少包含 `id`、创建/更新时间；可编辑聚合包含 `version`。ID 由服务端生成，不能延续“扫描最大 ID + 1”的并发生成方式。每种业务单据具有独立业务编号，与内部 ID 分离。

### 4.1 单位与精度

- 首版耗材基本单位为克，数量按整数毫克存储，前端展示克；采购公斤必须在入库前按固定换算转换。件数只允许正整数，实际时间按秒存储。
- 首版仅支持 CNY，单据金额使用整数分；单位成本使用十进制定点值（例如 PostgreSQL `NUMERIC`），计算到单据行后四舍五入到分，再汇总。JSON 中传递十进制字符串，不用二进制浮点作核心金额计算。
- 拒绝空字符串、非数值、负数量、不允许的小数精度及不匹配单位。价格零值允许，但必须显式输入。
- 时间戳统一 UTC，业务日期和报表按部署组织时区，默认 `Asia/Shanghai`。迁移时保留原时间值，无法解析的记录列入异常报告。

## 5. 状态与一致性规则

### 5.1 状态拆分

目标订单主状态为 `draft → confirmed → closed`，取消使用 `cancelled`；生产、交付和结算进度分别计算，不再用一个状态表达全部业务。

- 生产进度：未下达、待生产、生产中、部分完成、完成。
- 交付进度：未交付、部分交付、已交付。
- 结算进度：未收款、部分收款、已结清。
- 订单关闭要求数量义务已履行或经过有原因的关闭处理，且应收余额为零。允许完成生产但仍等待发货或收款。
- 草稿可删除；确认后仅允许作废/取消/归档。有关联单据时先处理在制任务、预留、未交付数量和资金余额。
- 重开订单不能自动冲销库存或财务记录；已交付数量、流水、收款继续有效，通过补充任务或变更单处理。

生产任务：`draft → released → in_progress → completed`；可暂停后恢复，未完成剩余量可取消。任务完成要求计划有效数量已达成、质检记录完整、未使用预留已释放。实际领料已发生时取消任务必须记录剩余物料处置。

采购单：`draft → confirmed → partially_received → received → closed`；未到货余额可取消。收付款结算独立展示，关闭要求到货义务处理完成且应付结清。

### 5.2 库存规则

现存数量 = 迁移期初数量 + 所有已过账流水的有符号变动量。

未领预留 = 有效预留量 − 已领量 − 已释放量；可用数量 = 现存数量 − 未领预留。禁止负库存及可用量小于零。

- 对预留领料必须同时减少现存和对应未领预留；普通出库只能使用未被其他任务预留的数量。
- 领料、退料、采购入库、退货、报废和冲销都使用显式业务动作。
- 盘点录入实盘数量，服务端计算差额并写流水。如果实盘不足以覆盖未领预留，必须先调整预留。
- 批次一般编辑只修改位置、备注等非余额字段。停用或归档不能删除流水和历史成本。
- 已过账记录通过反向单据更正。冲销原入库时也必须检查库存和预留是否允许；不能因为是冲销就放任负数。

### 5.3 并发、重试与跨模块原子性

所有过账动作使用幂等键：同键同请求返回同一结果，同键不同请求返回冲突。单据行与来源动作建立唯一约束，防止不同幂等键重复过账。

事务包含状态校验、余额校验、业务记录、流水、成本、审计和幂等回执。失败全部回滚。对批次、预留和单据按固定顺序加锁；一般编辑检查 `version`，版本不一致返回 409 并要求刷新。

邮件、设备调用、文件清理等外部副作用不在数据库事务中直接执行；先写待执行事件，成功提交后处理，失败可重试。禁止以 AI 对话记忆作为业务余额或单据的事实来源。

## 6. 经营核算口径

材料采用批次实际入库成本，领料时保存成本快照；退料按原领料成本回转，不使用当前采购价格。迁移历史批次成本未知时标为 `cost_unknown`，不能默认为零后展示确定利润。

设备成本 = 实际打印秒数 ÷ 3600 × 设备小时费率；人工成本 = 实际工时 × 人工费率；其他直接费用按单独条目录入。费率包含什么项目应在配置中说明，设备综合费率已包含电费时不能再次计电费。

任务实际成本 = 净领料成本 + 所有成功/失败尝试的设备与人工成本 + 其他直接费用。

订单管理毛利 = 订单有效金额 − 关联任务实际成本 − 订单其他直接费用。该指标不是会计净利润，未完工订单标为暂估；部分交付首版不计算会计收入确认。

预计成本和实际成本分别展示。实际耗材数量来自库存流水，打印尝试可分摊该耗用，不能再独立增加同一份材料成本。

订单确认产生应收；收款分配减少余额，预收在订单确认后分配。减少已确认订单金额使用贷项调整，已收超额部分进入待退款；退款关联原收款。应付按验收入库产生，采购退货使用贷项调整，已付超额部分记录供应商待退金额。资金记录不能直接删除。

## 7. 权限、界面与 AI

| 动作 | Owner | Staff 默认 | Viewer 默认 |
| --- | --- | --- | --- |
| 查看订单、生产、模型和库存 | 是 | 是 | 是 |
| 创建订单草稿、生产报工、普通领退料 | 是 | 是 | 否 |
| 确认采购、盘点过账、冲销、更改费率 | 是 | 否 | 否 |
| 查看成本、利润、资金及登记收付款 | 是 | 否 | 否 |
| 管理人员、权限、迁移及完整导出 | 是 | 否 | 否 |

目标权限使用动作能力，如 `production.report`、`inventory.post`、`purchase.confirm`、`finance.record`、`cost.view`；保留现有角色作为默认能力模板。后端鉴权以及响应字段裁剪必须与界面一致。Staff/Viewer 的订单查看可包含销售金额，但不能包含成本、利润和资金流水。

移动端优先支持领退料、报工、拍照、查单和异常记录；桌面 Web 优先支持主数据、报价、采购、排程和报表。沿用当前 Expo Web，先验证表格、批量操作和布局是否满足需求，再评估独立桌面前端。

AI 先提供查询、解释、提醒和草稿。过账、冲销、收付款必须展示具体单据、数量和金额，由具备能力的用户确认后调用统一业务服务；确认后仍重新检查权限、版本、库存与幂等键。AI 工具不能绕过 HTTP 接口执行同等动作时的规则，成本字段也要进行权限过滤。

## 8. 技术演进建议

保持 Express、Expo / React Native 和自托管架构；以模块化单体实现业务模块，不为首轮改造引入微服务。

建议新增结构（尚不存在）：

```text
backend/business-db/       PostgreSQL 连接、事务、业务迁移
backend/business-db/migrations/
backend/modules/           各领域的校验、服务和数据访问
  customers/ inventory/ production/ purchasing/ settlement/ reporting/
```

HTTP 路由负责协议、权限和输入解析，模块服务负责业务规则与事务，数据访问层负责查询和锁。现有订单服务逐步接入；AI、CSV 和 HTTP 共用服务。客户端继续在 `screens/`、`navigation/`、`utils/api.js` 下增加模块入口，较复杂模块再按职责拆分。

P0 在现有存储上修复规则并提取服务；P1 将核心业务迁移为 PostgreSQL 关系表，随后才添加生产、采购和结算模块。迁移后业务事实只有关系表一个写入来源，不能同时维护 JSONB 与关系表余额。

文件模式保留为原 MVP 的体验/迁移来源；完整 ERP 必须使用 PostgreSQL。文件模式下 ERP 页面和写接口给出明确不可用说明；如果将来需要 ERP 文件模式，必须另行设计和验证，不能默认为现有能力。

## 9. 迁移与历史兼容

1. 使用 [备份恢复手册](BACKUP_RESTORE.md) 创建业务数据、AI SQLite 和附件同一恢复点；在隔离环境恢复并演练。
2. 生成只读预检报告：ID、客户重复、订单行引用、无效数量/金额、缺失批次、负库存、附件缺失、时间解析和历史余额差异。业务异常由人工处理或明确标记，不静默丢弃。
3. 建立带版本的迁移工具、迁移映射和执行记录。支持 dry-run、重复执行不重复导入、失败事务回滚。
4. 历史客户仅建立候选匹配；同名不同电话不合并。保留订单原客户快照和原 ID 到新 ID 的映射。
5. 为缺乏稳定 ID 的订单行生成新 ID 并保存映射。未知打印耗时、材料成本、生产状态不推算成确定事实。
6. 在切换时点以当前批次余额建立可审计期初流水，旧流水作为历史参考保留；不得把旧流水再加入期初后重复累加。旧 `adjust.qty` 只解释为调整后数量。
7. 历史订单保存 `legacyStatus`。草稿映射为草稿，取消映射为取消，其余映射为确认订单并标记历史待核对；旧 `completed` 不推断已质检、已交付或已收款。历史单据不自动创建应收，启用结算时只对已核对的未结余额创建期初应收。
8. 停写后做最终迁移和对账，保留迁移前快照为只读。客户端 API 兼容层或版本升级须与切换一起验收，旧客户端不得通过旧库存编辑接口破坏新规则。
9. 回滚恢复完整迁移前备份和兼容的应用版本。新系统已有写入后不能直接恢复旧快照继续营业，必须停写、导出新增单据并核对处理。

对账至少比较订单数量/行数/有效金额、材料数量、逐批次数量、用户与角色、附件引用、审计保留和关系引用。成本未知及历史待核对记录要显示在报告中，不能以“导入成功”代替对账。
