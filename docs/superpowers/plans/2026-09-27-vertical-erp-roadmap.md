# 3D Manage 垂直 ERP 改造路线图

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
>
> 上述技能是计划模板中的执行约定；执行环境缺少对应技能时，使用本仓库可用工具逐项实施与复核，不假定这些技能已安装。本文为阶段路线图；每阶段必须先生成含具体代码、命令和测试的可执行子计划。本文不授权一次性实施全部阶段，也不要求本次派发子代理。

**Goal:** 将现有订单、模型与耗材管理系统逐步演进为 3D 打印工作室垂直 ERP。

**Architecture:** 采用模块化单体，复用 Express、Expo 和自托管能力。先统一库存与业务服务，再迁移核心数据至 PostgreSQL 关系表；生产、采购和经营结算依次接入同一业务事实来源。

**Tech Stack:** JavaScript、Expo / React Native / Web、Express、PostgreSQL、现有 AI SQLite、Node.js 内置测试、Docker Compose。

---

更新日期：2026-09-27。P0 已实现并完成自动化验收，未部署；P1–P6 尚未实施。全局业务规则见 [ERP 改造设计](../../ERP_TRANSFORMATION.md)，本文只负责阶段、代码入口、交付物和验收门槛。

## 1. 执行顺序

P0 一致性基础 → P1 主数据与关系存储 → P2 生产闭环 → P3 报价与成本 → P4 采购 → P5 交付、结算与经营报表 → P6 AI / 设备扩展。

P1 完成后可独立试点 ERP 主数据；P2 完成后可试点生产管理。P3–P5 完成并通过端到端验收后，才具备本文定义的 ERP 首版经营闭环。

每阶段只处理列出的范围。具体工作量在子计划完成后估算；当前不承诺人日或上线日期。

## 4. P1：主数据与 PostgreSQL 关系存储

目的：建立客户、供应商、默认仓库以及核心业务关系表，形成可演进的数据基础。

修改入口：`backend/utils/store.js`、`backend/config/runtime.js`、`backend/server.js`、核心业务路由、`backend/scripts/migrate-file-to-postgres.js`（仅处理旧迁移入口衔接）、`utils/api.js`、服务器能力识别及主数据页面。

新增入口：`backend/business-db/`、`backend/business-db/migrations/`、`backend/modules/customers/`、迁移命令、`tests/backend/erp-migration.test.cjs`、`tests/backend/erp-postgres.test.cjs`。迁移旧 JSONB 到关系表使用独立命令，不能冒用现有文件到 JSONB 迁移为已完成 ERP 迁移。

- [ ] 冻结实体字段、外键、唯一约束、精度、版本和索引；确定 API 兼容或升级方式。
- [ ] 建立事务入口和独立业务迁移版本；验证空库安装、重复启动和未知版本拒绝。
- [ ] 建立核心关系表：组织/用户、客户、供应商、仓库、材料、模型引用/版本、订单/行、批次、流水、审计、幂等回执及迁移映射。
- [ ] 实现只读预检与 dry-run，列出无效金额、数量、孤立引用、成本未知和历史状态待核对。
- [ ] 实现幂等数据迁移，保留旧 ID 映射、附件引用与审计；批次以切换期初建账。
- [ ] 将 HTTP、AI、CSV 的核心数据访问切到关系库，同事务写入单据、流水及审计。
- [ ] 提供客户、供应商、默认仓库页面；客户匹配由用户确认，订单保留快照。
- [ ] 服务端声明 ERP 能力；文件模式禁用 ERP 操作并提供可读说明；测试旧客户端写入限制。
- [ ] 在隔离恢复环境演练迁移、对账、失败恢复；更新备份和升级手册。

退出门槛：迁移重复执行不重复数据，失败不留下部分业务；逐批次余额和订单金额对账；并发写入无 ID 冲突；外键保护历史；AI 会话及受保护附件仍可访问。

## 5. P2：生产任务、人工排程与质检

- [ ] 冻结生产规格快照、任务、打印尝试、质检、预留和设备时段契约。
- [ ] 订单行生成任务，限制有效下达数量；补打记录原任务和原因。
- [ ] 实现设备启用/维护状态及人工时段分配，同设备重叠分配在事务中拒绝。
- [ ] 实现批次预留、领用和退料；领用释放相应预留且扣库存，取消释放未领预留。
- [ ] 实现开始、暂停、报工、质检和取消动作；记录实际数量、耗时及失败原因。
- [ ] 展示独立生产进度和合格产出余额；订单状态不直接制造产量事实。
- [ ] 验证部分完成、并发领料、失败补打、取消在制任务、超量质检和排程冲突。
- [ ] 验收设计文档 A01–A05，更新操作说明及交付记录。

退出门槛：订单行→任务→尝试→质检→耗材流水可追溯；取消不抹去实际消耗；预留和现存计算准确；打印产品报废不重复扣原料。

- [ ] 冻结单位成本精度、行金额取整、费率包含范围、批次成本和未知成本口径。
- [ ] 实现人工配置报价参数，保存数量、耗材、设备、人工及加价明细；支持手工报价。
- [ ] 报价确认转订单保存不可变价格及规格快照，禁止重复转换生成重复订单。
- [ ] 实现净领料成本、尝试设备/人工费用和额外费用，来源唯一；退料按原成本回转。
- [ ] 报价估计与实际结果分别展示；未知成本明确标记，未完工显示暂估。
- [ ] 增加成本能力控制及响应字段裁剪，验证 HTTP、导出与 AI 查询。

- [ ] 实现采购草稿和 Owner 确认，跟踪订购、已验收、已退货及取消余量。
- [ ] 实现分批验收入库，收货单、批次、库存流水和成本同事务写入。
- [ ] 实现采购退货，限制原收货数量和批次可用量；保留反向单据。

- [ ] 新订单确认建立应收、采购验收入库建立应付，来源唯一；历史仅录入已核对期初余额。

业务测试使用隔离数据目录或专用测试 PostgreSQL，不能连接实际工作室数据库。新阶段测试需要写明启动方式、环境变量、清理目标和预期结果；测试数据库的具体配置在子计划中给出。

