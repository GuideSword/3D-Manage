# 新手友好 README 改版设计

## 目标

重写仓库根目录 `README.md`，让第一次打开项目的读者能够快速回答三个问题：

1. 3D Manage 是什么、解决什么问题；
2. 应根据自己的环境选择哪种部署方式；
3. 部署后如何连接客户端并完成首次 Owner 初始化。

README 面向项目使用者、首次部署者和开发者。它应提供完成首轮部署所需的最短路径，同时把升级、备份、HTTPS 等深入内容链接到现有专项文档，避免首页变成难以浏览的完整运维手册。

## 采用方案

采用“分层入口式 README”。顶部先给出项目定位、交付形态、界面预览和核心能力；随后用部署导航表将读者分流到 Windows 一键部署、Docker 通用部署或本地开发；最后补充架构、权限、安全、运维和文档索引。

未采用以下方案：

- 单篇完整手册：虽然所有内容集中，但篇幅会掩盖首次部署的关键步骤；
- 极简首页加文档链接：页面简洁，但新手无法在 README 内直接完成部署和首次初始化。

## README 信息架构

### 1. 首屏概览

- 项目名称与一句话定位；
- 明确系统由 Expo/React Native 客户端和自托管 Express 后端组成；
- 说明客户端运行时填写服务器地址，安装包不绑定特定客户域名；
- 使用仓库中已有的实际界面截图展示项目外观，不新增或伪造产品图片。

### 2. 核心能力

以短表格或紧凑列表介绍：

- 订单创建、查询和状态流转；
- 模型资料与受保护附件；
- 耗材、入库、出库和库存调整；
- Owner、Staff、Viewer 分级权限；
- 审计记录；
- 可选的小鲤 AI 助手和 OSS 文件存储。

此处只描述当前代码已经具备的能力，不把需求文档中的未来规划写成已实现功能。

### 3. 部署方式选择

用一张对照表列出三个入口：

| 场景 | 推荐方式 | 适用对象 |
| --- | --- | --- |
| Windows 10/11 主机 | 一键后端脚本 | 希望最少命令完成部署的新手 |
| x86_64 Linux 主机 | Docker Compose | 服务器管理员和 Linux 部署者 |
| 修改与调试源码 | Expo + 本地 Express | 开发者 |

每个入口直接链接到同一 README 中对应的小节，并标明生产部署与开发启动不是同一套数据和安全配置。

### 4. Windows 一键部署

提供最短的编号步骤：

1. 准备 Node.js、Docker Desktop/winget 所需环境并获取源码；
2. 双击 `一键安装并启动后端.bat`；
3. 等待 PostgreSQL 与应用容器健康，并记录脚本显示的服务地址；
4. 运行 `获取初始化令牌.bat` 获取一次性令牌；
5. 在客户端输入服务地址，填写组织和 Owner 信息完成初始化；
6. 后续使用 `一键启动后端.bat` 恢复服务。

说明默认宿主机端口为 `5800`，遇到冲突时脚本会引导清理占用方或选择新端口。一键脚本仅管理 Docker 后端，不安装或启动 Expo 客户端。

### 5. Docker 通用部署

提供可以复制执行的命令序列：

```powershell
node deploy/init-config.mjs
docker compose up -d --build
docker compose ps
curl.exe http://localhost:5800/api/system/info
```

同时给出 Linux 对应的 `curl` 写法。说明配置生成器不会覆盖已有 `.env`，健康接口应返回正确的产品名、服务器 ID 和 API 版本。公网部署必须继续阅读 HTTPS 章节或自托管文档，不能直接暴露明文 HTTP。本阶段只把 x86_64 Linux 和 Windows Docker Desktop 写作已验证的部署环境。

### 6. 客户端连接与首次初始化

解释后端启动不是全部流程：用户仍需安装或运行客户端，然后输入局域网地址或 HTTPS 域名。首次连接使用 `BOOTSTRAP_TOKEN` 创建唯一 Owner；系统没有公开注册入口，其他 Staff 和 Viewer 由 Owner 在设置页创建。

### 7. 本地开发

保留并完善现有开发命令：

```powershell
npm install
npm --prefix backend install
npm run start:all
```

补充前后端分别启动、Web/Android 入口和主要验证命令。明确开发脚本使用本地文件存储及临时开发密钥，不等同于生产部署。

### 8. 架构与权限

用简洁文本流展示：

```text
Expo / React Native 客户端 → Express API → PostgreSQL / AI SQLite / 上传目录
```

权限表只表达稳定的角色边界：Owner 负责系统和用户管理，Staff 负责日常业务编辑，Viewer 只读。详细模块级权限以代码和需求文档为准，不在 README 中制造未经验证的逐项权限矩阵。

### 9. 数据、安全与运维

醒目标注三个持久化目录：

- `runtime/postgres`：业务数据；
- `runtime/data`：AI SQLite 数据；
- `runtime/uploads`：本地上传文件。

说明删除 `runtime/` 会造成数据丢失；生产密钥只保存在后端；公网需要受信任 HTTPS；Web 来源需要精确配置 CORS。列出查看状态、查看日志、停止和启动服务的常用命令，并链接备份恢复和升级手册。

### 10. 故障排查与文档索引

README 只覆盖最常见的启动问题：Docker 未启动、端口冲突、健康检查失败、客户端无法访问服务器。每项给出一个直接检查动作，再链接到：

- `docs/SELF_HOSTING.md`；
- `docs/UPGRADE.md`；
- `docs/BACKUP_RESTORE.md`；
- `docs/RELEASE_CHECKLIST.md`；
- `backend/README.md`。

## 内容准确性与边界

- 所有命令以仓库现有 `package.json`、Compose 文件和部署脚本为准；
- 不在 README 中暴露 `.env` 的真实值、构建账户密钥或用户数据；
- 不承诺 ARM64、多副本部署、公开注册或未经验证的平台能力；
- 保留现有专项文档作为权威细节来源，README 负责导航和首次成功路径；
- 本次只修改根 README，不重写已有部署、升级或备份文档，也不触碰当前工作区中的其他未提交改动。

## 验证方式

完成改版后执行以下检查：

1. 核对 README 中的命令、脚本名、端口、目录和链接均真实存在；
2. 检查 Markdown 标题层级、表格、代码块、图片路径和站内锚点；
3. 运行仓库已有的自托管静态验证，确认文档描述没有违背部署契约；
4. 查看 Git diff，确认只修改计划内的 README，并保留其他未提交工作；
5. 从新用户视角通读 Windows、Docker 和开发三条路径，确保每条路径都有明确的下一步和成功标志。

## 完成标准

- 读者在首屏能够理解产品用途和客户端/后端交付方式；
- Windows 与 Docker 用户都能在 README 内找到可执行的部署步骤；
- 首次 Owner 初始化不再依赖读者自行猜测；
- 项目功能、技术架构、权限、安全和数据位置均有简洁说明；
- 深入运维内容可通过有效链接继续阅读；
- README 描述与当前仓库实现一致。
