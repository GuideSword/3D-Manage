# Agent 多图发送与独立 AI 服务配置设计

## 背景

当前 AI 助手选择图片后会在 Android/Expo 54 环境报错：`Cannot read property 'Base64' of undefined`。原因是客户端从 `expo-file-system` 现代入口导入模块，却调用旧版 `FileSystem.EncodingType.Base64`。当前实现还存在附件父子状态不同步、失败后草稿丢失、图片请求缺少服务端校验，以及把聊天大模型与 Embedding 强制共用 API Key 等问题。

后端数据库已经为 LLM 和 Embedding 保留独立字段，但保存路由要求两种 Key 同时存在，客户端又直接把 LLM 的 Base URL 和 API Key 复制给 Embedding。Embedding 因此既不独立，也无法作为可选增强能力使用。现有模型向量表和余弦搜索只有基础结构，没有完成存量回填和随模型数据更新的索引生命周期。

## 目标

- 一条消息支持发送多张图片，也支持不输入文字、只发送图片。
- 修复 Expo 54 图片读取错误，避免旧附件重复发送，并保证发送失败时不丢失草稿。
- 由系统实际探测大模型的图片能力，不让用户手动声明模型是否支持图片。
- 大模型配置与 Embedding 配置完全独立；Embedding 不配置时，其他 Agent 功能正常可用。
- API Key 只写不可读，保存后客户端只能得知“已配置”，不能查看完整值、尾号或可还原掩码。
- 补齐当前用户的模型 Embedding 存量回填、新增、更新、删除和检索隔离。

## 非目标

- 不引入通用 AI Provider 插件系统。
- Embedding 仍使用项目现有的 MiniMax 专用协议，本阶段不新增其他 Embedding 协议。
- 不新增耗材语义搜索；本阶段只完成模型语义索引。
- 不在本阶段实现长对话压缩和历史图片召回；这些由独立的分层记忆设计承接。

## 设置页交互

设置页采用已确认的“状态卡片 + 按需展开”布局。

### 聊天大模型卡片

聊天大模型是必填服务。摘要状态显示 Base URL、模型名、连接状态和系统探测出的图片能力，不显示 API Key。编辑状态提供 Base URL、模型名和空白 API Key 输入框：

- 首次配置必须填写 API Key。
- 已配置后输入框始终为空，提示“API Key 已配置；输入新 Key 可替换”。
- 留空保存表示继续使用服务端已有 Key。
- 输入新值表示用新 Key 替换旧 Key。
- Base URL、模型名或 Key 变化后，旧的连接状态和图片能力状态立即失效。

图片能力状态为 `untested`、`testing`、`vision`、`text_only` 或 `error`，界面分别显示“尚未检测”“检测中”“支持图片”“仅文本”和“检测失败”。用户不能手动修改该状态。

### Embedding 卡片

Embedding 卡片默认折叠并明确标记为“可选的语义搜索增强”。展开后独立填写 Base URL、API Key、模型名和 Group ID，不继承大模型字段。

- 四个字段全部为空表示未启用。
- 开启时四个字段必须完整；已保存的 API Key 可留空沿用。
- 新候选配置测试失败时不替换当前可用配置。
- 用户可以明确关闭 Embedding；关闭后聊天、图片、订单工具、库存工具和关键词模型搜索继续可用。

## 密钥与配置 API

保留 `/api/agent/keys` 路由族，调整为以下契约：

- `GET /api/agent/keys`：返回公开配置、`llm_api_key_configured`、`embed_api_key_configured`、图片能力状态和索引状态；永不返回密钥、密钥尾号或密文。
- `POST /api/agent/keys/test`：将请求中的候选公开字段和可选新 Key 与服务端已有 Key 合并后测试，不持久化。分别返回 LLM、图片能力和 Embedding 结果。
- `PUT /api/agent/keys`：在服务端测试合并后的候选配置；LLM 连接成功后才原子替换 LLM 配置。图片探测失败不阻止保存，而是保存为 `text_only` 或 `error`。启用 Embedding 时只有 Embedding 测试成功才替换其配置。

首次保存必须提供 LLM Key。已有 Key 时，缺省或空白 Key 表示保留。Embedding 使用显式 `enabled` 字段；`enabled: false` 清除其可用状态和索引激活指针，但不影响 LLM。所有接口只允许当前认证用户操作自己的配置。

密钥继续使用 AES-256-GCM 加密。日志、审计记录、错误响应和测试输出不得包含明文 Key、密文、Authorization 请求头或图片 Base64。

## 图片能力探测

系统用仓库内固定的小型 PNG 测试图进行真实多模态请求。测试图包含一个四位数字，探测提示要求模型只返回图中数字；返回值匹配才认定为 `vision`。模型明确拒绝图片或返回错误时记为 `text_only`，网络、超时或无法分类的服务错误记为 `error`。

探测使用较小输出预算和短超时。已有配置状态为 `untested` 时，用户点击图片按钮会先触发探测；通过后继续选择图片，未通过则跳转或提示检查 AI 设置。配置变化会使旧结果失效，不能沿用其他 Base URL、模型或 Key 的结果。

## 客户端图片状态与发送流程

聊天页面是待发送附件的唯一状态所有者，图片组件变为受控组件，接收 `images`、`onAdd` 和 `onRemove`。这消除父组件已清空、子组件仍保留旧缩略图的问题。

图片选择支持一次多选和分次追加。每张附件只在 React 状态保存本地 URI、名称、MIME 和字节数；Base64 不长期保存在组件状态中。缩略图提供可见的删除按钮，不依赖长按。

限制如下：

- 每条消息最多 4 张图片。
- 单张原始文件不超过 4 MB。
- 一条消息所有原始图片合计不超过 6 MB。
- 接受 JPEG、PNG 和 WebP；其他格式在发送前给出明确提示。

发送前由独立图片读取适配器校验 URI 和文件存在性，再使用 Expo 54 的 `File` API 读取 Base64。适配器输出标准附件对象和 data URL，页面不直接访问 File System 枚举。发送按钮在有文字或有图片时可用；只有图片时，服务端内部使用“请分析这些图片”作为模型输入，客户端消息气泡不显示这段自动文字。

客户端在图片准备和请求期间禁止重复提交。输入文字与附件快照直到服务端发送 `done` 事件后才清空；读取、网络或模型调用失败时恢复快照并显示重试入口。

## 服务端图片校验与多模态消息

`POST /api/agent/chat` 在开始 SSE 响应前完成请求结构校验。服务端接受文字为空但图片非空的消息，并为模型补充内部提示。服务端再次验证：

- 图片数组数量不超过 4。
- data URL 语法正确且 Base64 可解码。
- 声明 MIME 与解码后的文件签名一致。
- MIME 只允许 JPEG、PNG、WebP。
- 单张和总解码字节数符合客户端相同限制。
- 当前模型图片能力状态为 `vision`。

错误使用稳定代码：`IMAGE_READ_FAILED`、`IMAGE_TYPE_UNSUPPORTED`、`IMAGE_TOO_LARGE`、`IMAGE_TOTAL_TOO_LARGE`、`IMAGE_LIMIT_EXCEEDED`、`IMAGE_CAPABILITY_UNTESTED` 和 `IMAGE_CAPABILITY_UNSUPPORTED`。客户端将这些代码映射为中文操作提示。

本阶段只把图片用于当前模型请求。持久化消息只保存图片名称、MIME、大小和“当前轮包含图片”的占位信息，不把 data URL 写入 SQLite。后续会话图片文件保存与召回由分层记忆阶段实现。

## Embedding 索引模型

现有 `user_settings` 的 Embedding 字段迁移为可空，并增加 LLM 图片能力状态与检测时间。模型向量使用按用户隔离的新结构，至少保存：

- `user_id`
- `asset_id`
- `config_fingerprint`
- `source_text`
- `source_hash`
- `embedding`
- `vector_dim`
- `status`
- `last_error`
- `updated_at`

`config_fingerprint` 由规范化后的 Embedding Base URL、模型名、Group ID 和协议版本生成，不包含 API Key。唯一约束覆盖 `user_id + asset_id + config_fingerprint`，确保不同用户或不同向量空间不会混合比较。

另存每个用户当前配置的索引进度：`idle`、`building`、`ready`、`partial` 或 `error`，以及总数、成功数、失败数和最后错误摘要。任务必须幂等且可恢复；进程中断后，下次打开设置页或请求语义搜索时可以继续缺失项目。

## 索引生命周期

Embedding 配置测试并保存成功后，为当前用户启动存量模型回填。索引源文本由模型名称、描述、标签和当前版本组成，`source_hash` 用于判断内容是否变化。

- 新增模型：为执行操作且已启用 Embedding 的当前用户排队生成向量。
- 更新模型：新的源哈希使旧向量变为过期，并为当前用户排队重建。
- 删除模型：删除所有用户对应资产的向量行。
- 其他用户：不因别人的写操作立即消耗其 API 额度；其下次打开设置页或调用语义搜索时，系统按自己的配置补齐缺失或过期行。

语义搜索只在当前用户的 Embedding 配置可用且至少存在可搜索索引时注册给 LLM。未启用、配置失败或完全没有索引时，只注册关键词搜索。部分索引可用时返回已有结果，并在后台继续补齐，同时在结果元数据中标明索引不完整。

## 错误处理

- 候选 LLM 配置失败：保留旧配置和旧能力状态。
- 图片探测失败：区分确认不支持与临时检测错误；不把临时网络错误误判为仅文本。
- 候选 Embedding 配置失败：不启用或不替换旧 Embedding。
- 单个模型向量生成失败：任务记为 `partial`，记录不含敏感内容的错误摘要并继续其他模型。
- 发送图片失败：保留输入和附件，避免产生空白助手消息；允许用户修改后重试。
- 模型接口在实际发送时拒绝图片：标准化为 `IMAGE_CAPABILITY_UNSUPPORTED`，使能力状态失效并引导重新检测。

## 验证

图片回归测试先用旧式 File System namespace 模拟截图中的 `EncodingType.Base64` 失败，再验证新的读取适配器不依赖该字段。客户端测试覆盖多选、追加、删除、纯图片消息、格式与大小限制、成功清空、失败恢复和旧附件不重复发送。

服务端测试覆盖图片数组及 data URL 校验、文件签名检查、总大小限制、文本模型拒绝图片和内部纯图片提示。能力探测测试覆盖真实支持、明确不支持、答案不匹配、超时和配置变化失效。

配置测试断言：

- GET 响应和日志中没有任何形式的密钥。
- 首次 LLM 配置要求 Key，后续空白 Key 保留旧值，新 Key 才替换。
- Embedding 完全不配置时聊天可用。
- Embedding 部分填写被拒绝，完整且测试成功后才启用。
- LLM 与 Embedding 可以使用不同 Base URL、Key 和模型。

索引测试使用可预测的模拟向量 Provider，覆盖存量回填、新增、更新、删除、失败续跑、用户隔离、配置指纹隔离、部分索引结果和未配置时关键词降级。最后运行客户端验证、后端验证和 Expo Web 导出，并在 Android Expo 环境重新执行最初的选图场景。

## 完成标准

- Android 不再出现 `Base64 of undefined`，同一条消息可以可靠发送 1–4 张图片。
- 纯图片消息可发送；失败不丢失文字或附件；成功后不存在旧附件重复发送。
- 用户不能读取任何已保存 API Key。
- 系统自动而准确地区分图片模型、文本模型和临时检测失败。
- 只配置 LLM 时所有非语义 Agent 功能正常工作。
- 配置独立 Embedding 后，当前用户可以搜索存量、新增和更新后的模型语义索引。
