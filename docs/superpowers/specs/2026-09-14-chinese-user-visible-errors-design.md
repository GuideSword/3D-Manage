# 用户可见报错中文化设计

## 目标

将当前中文使用环境中最终用户可见的前端报错提示和后端 API 错误响应统一为自然、明确的中文，同时不改变接口行为、业务逻辑和机器可读错误码。

## 范围

- 修改前端界面通过弹窗、页面状态、Toast 或错误区域展示的英文报错。
- 修改后端 API 响应体中 `error` 或面向用户的 `message` 字段所返回的英文报错。
- 修改会被上述界面或 API 直接透传给最终用户的内部异常消息。
- 不修改仅供开发人员使用的控制台日志、部署脚本提示、迁移脚本提示和测试断言。
- 不翻译稳定的机器标识，包括错误码、环境变量、配置键、HTTP 状态、文件扩展名和第三方服务名称。

## 实现方式

采用逐处翻译现有文案的方式，不引入国际化框架或集中式错误字典。翻译时保留现有响应状态码、响应结构和控制流程；仅替换用户可见的字符串。

对动态错误保留有助于排障的安全信息，例如 HTTP 状态、文件名或字段名。第三方服务、数据库及底层运行时返回的原始英文异常不得无条件直接暴露给最终用户；已知场景使用具体中文提示，未知场景使用当前操作对应的中文兜底提示。

## 文案规则

- 使用简体中文，语气简洁、可行动，例如“登录失败，请检查邮箱和密码”。
- 同一类资源统一使用项目现有术语：订单、模型、耗材、库存批次、附件、服务器和智能助手。
- “未找到”“无权限”“未登录”“参数无效”“操作失败”等状态应明确区分。
- 保留必要的技术名词，例如 `PNG`、`PDF`、`HTTP 404`、`API`、`OSS`。
- 不在用户提示中暴露密钥、内部路径、SQL、堆栈或服务端配置细节。

## 兼容性

现有客户端仍从相同字段读取错误文本，现有自动化仍可依赖原错误码和 HTTP 状态。除文案断言外，不需要调用方迁移。

## 验证

- 运行后端现有验证测试，确认响应结构、状态码及业务行为未改变。
- 运行客户端现有测试，确认错误处理路径仍可执行。
- 对前端展示点和后端 API 响应点执行静态扫描，人工审阅剩余英文字符串，排除机器标识及非用户可见内容。
- 为关键通用错误路径补充或更新中文文案断言，防止英文提示回归。

## 验收标准

最终用户在应用界面及 API 错误响应中不再看到项目自有的英文报错；错误码、HTTP 状态和业务行为保持不变；开发日志与运维脚本不因本次改动产生无关变化。
